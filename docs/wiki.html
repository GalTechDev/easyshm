DOCUMENTATION

RÉFÉRENCE py-easyshm 0.1.0 · Python ≥ 3.8

Documentation

Tout ce qu'il faut pour partager de la mémoire entre processus Python : création de segments, vues typées, signalisation et détails de plateforme.

01

Installation

$ pip install py-easyshm

NumPy est installé comme dépendance. PyTorch est optionnel et n'est requis que pour la vue torch.

02

La classe EasySHM

L'unique point d'entrée. Tous les processus qui ouvrent le même name partagent la même mémoire : le premier crée le segment, les suivants le rejoignent (size est alors ignoré).

codesignature 

EasySHM(
    name: str,
    size: int = 4096,
    auto_grow: bool = True,
    auto_shrink: bool = False,
    mode: int = 0o600,
    auto_recover_mutex: bool = True,
    pinned: bool = False,
    on_pin_fail: str = "error",
    persistent: bool = False,
)
Paramètre Description
name Identifiant unique partagé par tous les processus.
size Capacité initiale en octets. Ignorée si le segment existe déjà.
auto_grow write() double la capacité quand les données ne tiennent pas. Si False, lève OverflowError.
auto_shrink Divise la capacité par deux quand les données en utilisent moins de 25 % (jamais sous la taille initiale).
mode Permissions POSIX du fichier de segment (propriétaire uniquement par défaut).
auto_recover_mutex Reprend silencieusement un mutex abandonné par un processus planté. Si False, lève LockAbandonedError.
pinned Verrouille le segment en RAM physique (mlock / VirtualLock) pour qu'il ne soit jamais swappé.
on_pin_fail "error" lève une exception si le verrouillage échoue ; toute autre valeur affiche seulement un avertissement.
persistent Si False, le dernier processus à appeler close() supprime le segment. Si True, il survit jusqu'à destroy() (POSIX uniquement : Windows le libère toujours avec le dernier handle).
03

Lecture & écriture

Accès brut aux octets. Chaque appel est protégé par le mutex inter-processus, et chaque write() incrémente le compteur de séquence et réveille les autres processus.

codeexample.py 

from easyshm import EasySHM

shm = EasySHM("shared_bus", size=1024 * 1024)

# Écrire des octets (truncate=True remplace data_size)
shm.write(b"Hello RAM!", offset=0, truncate=True)

# Lire : size=None lit jusqu'à data_size
data = shm.read()               # b"Hello RAM!"
part = shm.read(size=5, offset=0)  # b"Hello"

# Vue memoryview sans copie
mv = shm.read_view()

# Redimensionnement manuel
shm.resize(4 * 1024 * 1024)
write(data, offset=0, truncate=False) Écrit des bytes, bytearray ou memoryview. Agrandit le segment si besoin.
read(size=None, offset=0) Renvoie une copie en bytes.
read_view(offset=0, size=None) Renvoie une memoryview zéro-copie sur le buffer.
resize(new_capacity) Agrandit ou réduit le segment ; les autres processus suivent automatiquement.
04

Vues zéro-copie

as_view(name, **kwargs) mappe un objet Python typé directement sur le buffer partagé. Rien n'est copié : modifier l'objet modifie la mémoire vue par tous les processus.

numpy
shape, dtype="uint8", offset=0
struct
type=ctypes.Structure, offset=0
torch
shape, dtype="float32", offset=0

codeviews.py 

import ctypes

# NumPy : une image 1080p partagée
img = shm.as_view("numpy", shape=(1080, 1920, 3), dtype="uint8")
img[:] = 255  # écran blanc pour tous les processus

# Structure C
class Player(ctypes.Structure):
    _fields_ = [("x", ctypes.c_int), ("y", ctypes.c_int)]

p = shm.as_view("struct", type=Player)
p.x = 100

# Tenseur PyTorch (CPU)
t = shm.as_view("torch", shape=(10,))

Vues personnalisées

Le registre est extensible : héritez de SHMView, implémentez map_buffer() et enregistrez-la sous un nouveau nom.

from easyshm.views import ViewRegistry, SHMView

class BytesView(SHMView):
    def map_buffer(self, buffer, **kwargs):
        offset = kwargs.get("offset", 0)
        return buffer[offset:offset + kwargs["size"]]

ViewRegistry.register("bytes", BytesView())
raw = shm.as_view("bytes", size=16)
warning Une vue pointe sur le segment de données courant. Après un redimensionnement (par n'importe quel processus), redemandez la vue, par exemple depuis un callback on_resize(). as_ndarray() est obsolète : utilisez as_view("numpy", ...).
05

Signalisation inter-processus

Au lieu de scruter la mémoire en boucle, bloquez sur un objet noyau jusqu'à ce qu'un autre processus écrive. Deux styles sont disponibles : attente bloquante ou callbacks en arrière-plan.

codelistener.py 

# Style 1 : attente bloquante (timeout en secondes, None = infini)
if shm.wait_update(timeout=5.0):
    print("Données mises à jour :", shm.read())

# Style 2 : callbacks exécutés par le thread d'écoute
shm.on_update(lambda: print("write_seq =", shm.write_seq))
shm.on_resize(lambda cap: print("nouvelle capacité :", cap))
  • play_arrow wait_update() renvoie True si un autre processus a écrit depuis la dernière mise à jour signalée (une écriture entre deux appels n'est jamais perdue, plusieurs écritures peuvent être signalées d'un coup), False en cas de timeout. Une instance n'est pas réveillée par ses propres écritures.
  • play_arrow Les callbacks on_update(cb) ne prennent aucun argument ; ceux de on_resize(cb) reçoivent la nouvelle capacité. Ils tournent dans un thread d'écoute démarré avec le premier callback : sans callback, aucun thread ne ralentit vos écritures.
  • play_arrow Les exceptions levées dans les callbacks sont ignorées pour ne jamais tuer le thread d'écoute.
06

Métadonnées & cycle de vie

.data_size
Octets de données effectivement écrits.
.capacity
Taille actuellement allouée en octets.
.write_seq
Compteur monotone, incrémenté à chaque écriture.
shm.close()    # libère ce processus ; le dernier utilisateur supprime le segment
shm.destroy()  # supprime tout immédiatement, même s'il reste des utilisateurs

with EasySHM("bus") as shm:  # close() automatique
    shm.write(b"ping")

Chaque processus qui tient le segment garde un verrou partagé dessus, libéré par le noyau même si le processus plante. Au close(), si plus aucun autre processus ne le tient, tous les objets OS sont supprimés (données, segment de contrôle, fichier de verrou, sémaphore sous macOS). Les autres utilisateurs continuent normalement. Passez persistent=True pour conserver les données après la dernière fermeture.

07

Erreurs

LockAbandonedError Le mutex était détenu par un processus qui a planté (uniquement si auto_recover_mutex=False). Détecté sous Windows comme sous Linux/macOS.
ProtocolIncompatibilityError Le segment existant a été créé par une version de protocole EasySHM incompatible. Supprimez-le avec EasySHM.unlink(name).
CorruptedSegmentError Le segment existe mais son en-tête de contrôle est corrompu. Rien n'est écrasé ; supprimez-le avec EasySHM.unlink(name).
OverflowError Les données dépassent la capacité alors que auto_grow=False.
TimeoutError Le verrou IPC n'a pas pu être acquis pour l'écriture. 
from easyshm import EasySHM, CorruptedSegmentError, ProtocolIncompatibilityError

try:
    shm = EasySHM("bus")
except (CorruptedSegmentError, ProtocolIncompatibilityError):
    EasySHM.unlink("bus")  # supprime le segment sans l'ouvrir
    shm = EasySHM("bus")
08

Implémentation Windows

Les segments sont des file mappings nommés. La signalisation utilise des Named Events à réinitialisation manuelle dans l'espace de session Local\ : aucun droit administrateur n'est nécessaire.

bolt Une écriture appelle SetEvent puis ResetEvent, ce qui réveille tous les processus en attente d'un coup. Le thread d'écoute vérifie aussi toutes les 100 ms par sécurité.
09

Implémentation Linux / macOS

Les segments sont des fichiers mappés en mémoire dans /dev/shm (tmpfs en RAM), avec repli sur le dossier temporaire s'il n'existe pas. Sous Linux, la signalisation est un futex posé sur le mot write_seq de l'en-tête partagé : une écriture réveille tous les processus en attente d'un coup, sans jeton résiduel ni réveil perdu. macOS utilise des sémaphores POSIX nommés. Le mutex repose sur flock, et les noms sont préfixés par l'uid, ce qui isole les utilisateurs entre eux.

terminal Astuce : inspectez les segments actifs avec ls -l /dev/shm/easyshm_*.
10

Fonctionnement interne

Chaque objet EasySHM se compose d'un segment de contrôle de 256 octets (_ctrl) et d'un segment de données versionné (_d0, _d1…). Un redimensionnement crée un nouveau segment, y copie les données, puis incrémente seg_version : les autres processus le détectent et se remappent.
